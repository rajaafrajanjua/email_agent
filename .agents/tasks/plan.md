## Key Design Decisions

**D1 — Separate verifier module.**
`email_verifier.py` is a standalone module with no imports from the rest of the
project. It reads GMAIL_ADDRESS from `.env` via `python-dotenv` (already a
transitive dep) or falls back to `"verify@mext-check.local"`. This keeps the
module testable in isolation.

**D2 — dns.resolver (dnspython) for MX lookup.**
dnspython==2.6.1 is pinned. The SMTP probe connects to the first MX record
(lowest preference). If MX lookup raises `NXDOMAIN`, `NoAnswer`, or `NoNameservers`,
reason is `"no_mx"` and valid=False.

**D3 — SMTP probe result mapping.**
- 250/251 → valid=True, reason="ok"
- 550/551/552/553 → valid=False, reason="smtp_reject"
- 421/450/451/452 (tempfail) → valid=True, reason="unverifiable"
- Connection timeout / refused / OSError → valid=True, reason="unverifiable"
This is conservative: unverifiable addresses pass through (they were likely
blocked by the server), so we never silently drop deliverable addresses.

**D4 — JSON cache keyed by normalised email.**
Cache file: `verify_cache.json` in the project root. Key = email.lower().strip().
Cache is loaded once at module import, written after each new probe. TTL: 30 days
(results older than 30 days are re-verified on next use).

**D5 — `--skip-verify` flag on `import`.**
Default is verify ON so the user gets protection without extra flags. Adding
`--skip-verify` to the import subparser lets the user bypass when testing or
when they know the list is clean.

**D6 — `verify-queue` command.**
Operates on `status='queued'` by default; adds `status='sent'` to the scan when
`--fix` is NOT specified (retrospective report only). With `--fix`, only queued
entries are patched (marking sent ones failed would corrupt history).

**D7 — Python executable.**
All verify commands use `C:\Users\Raja\.local\bin\python3.14.exe`.
